`shared_data` (5 запусків, адреса `value` в усіх запусках однакова для Thread 1, Thread 2 і Main):


Між запусками адреса змінюється (ASLR), але в межах одного запуску вона однакова для всіх трьох. У всіх п'яти запусках фінальне `value` дорівнювало 200, але це залежить від порядку виконання threads: якби Thread 2 встиг записати значення раніше, фінальним було б 100.

**Прогноз:** Прогноз 2: адреса value буде однакова в обох threads і в main, бо value це глобальна змінна,
а threads одного process мають спільний address space. Фінальне значення залежить від того,
який thread записав останнім (у моїх запусках 200).

`thread_stacks` (локальна змінна `local`):

```
Run 1:
Thread 1: local=10, address=0x7593d2cc7eb0
Thread 2: local=20, address=0x7593d24c6eb0
```

Те саме у запусках 2 і 3: адреси різні.

**Прогноз:** адреси будуть різні. Результат збігся.

Висновок: global variable (дані process) спільна для threads, а local variable лежить у stack конкретного thread, тому в різних threads різні адреси.

```
Process
│
├── Code   ← shared
├── Data   ← shared
├── Heap   ← shared
│
├── Thread 1
│   └── Stack 1
│
└── Thread 2
    └── Stack 2
```

## 4. Lost update і race condition

У C `counter++` виглядає як одна операція, але концептуально це три кроки: READ counter, ADD 1, WRITE counter. Якщо два threads перемежовуються між кроками, виходить lost update. Нехай `counter = 100`:

```
Thread A        Thread B
READ 100
                READ 100
ADD → 101
                ADD → 101
WRITE 101
                WRITE 101
```

Очікували 102, отримали 101: один інкремент втрачено. Тому сумарний результат менший за 2000000.

- Shared state: змінна `counter`.
- Concurrent writers: два threads (`thread1` і `thread2`).
- Critical operation: `counter++`.

## 5. Machine instructions для `counter++`

Фрагмент `objdump -d -M intel race` для функції `increment` (компіляція без оптимізації):

```
11bf: mov rax,QWORD PTR [rip+0x2e52]   # 4018 <counter>   ← READ
11c6: add rax,0x1                                           ← ADD
11ca: mov QWORD PTR [rip+0x2e47],rax   # 4018 <counter>   ← WRITE
```

Так, `counter++` на рівні виконання складається з трьох окремих instructions: прочитати `counter` у регістр, додати 1, записати назад у пам'ять. Між ними scheduler може перемкнути thread або інше ядро CPU може змінити `counter`, тому ця операція **не є неподільною (atomic)**. Це зв'язок із Module 2: C statement → machine instructions → CPU execution.

## 7. Чому mutex виправив проблему

`pthread_mutex_lock()` дозволяє лише одному thread увійти в critical section (`counter++`). Інший thread, який намагається захопити той самий mutex, чекає, доки перший не викличе `pthread_mutex_unlock()`. Це mutual exclusion: READ, ADD і WRITE одного thread не перемежовуються з такою самою послідовністю в іншому. Тому втрачених оновлень немає, і результат завжди 2000000.

Де ставити lock. Якщо поставити lock навколо всього циклу (1 000 000 інкрементів), один thread утримуватиме mutex весь цей час, а другий чекатиме, і про паралельне виконання не буде й мови. Критична секція має бути достатньою для коректності, але без потреби не надто великою.

Synchronization має вартість:

| Program | Run 1 | Run 2 | Run 3 |
|---|---|---|---|
| race | 0.009 s | 0.009 s | 0.009 s |
| mutex_counter | 0.062 s | 0.075 s | 0.086 s |

**Прогноз:** я вважав, що `mutex_counter` буде швидшим. Прогноз хибний: `mutex_counter` повільніший приблизно в 7–9 разів. Це лише приблизні вимірювання, не точний benchmark. Причина: кожен інкремент проходить через lock/unlock, а threads змагаються за mutex (lock contention) і часто змушені чекати.

## 9. `shared_heap.c` і `thread_result.c`

```
Worker: value=110 address=0x60d7705122a0
Main: value=110 address=0x60d7705122a0
```

- `data` виділено через `malloc`, тому він лежить у **heap**.
- Worker бачить ту саму пам'ять: адреса однакова, значення 110 видно й у main.
- Це так, бо heap спільний для всіх threads одного process.
- Якби декілька threads одночасно виконували `data->value += 10`, це була б така сама race condition, як і з `counter++`.

`thread_result`: `Result = 144`. Не можна написати `int result = value * value; return &result;`, бо `result` локальна змінна в stack цього thread. Коли функція завершується, її stack frame (і `result`) перестає існувати, і повернений вказівник вказуватиме на недійсну пам'ять. Тому результат виділяють у heap через `malloc`, а main після `pthread_join()` читає його й звільняє через `free`.

## 10. Схема deadlock

```
Thread 1: lock(mutex1) → lock(mutex2)
Thread 2: lock(mutex2) → lock(mutex1)
```

```
Thread 1                 Thread 2
lock mutex1              lock mutex2
   │                        │
   ▼                        ▼
чекає mutex2  ◄──────  володіє mutex2
володіє mutex1 ──────►  чекає mutex1
         DEADLOCK
```

Circular wait: Thread 1 → mutex2 → Thread 2 → mutex1 → Thread 1.

**Прогноз:** я вважав, що threads виведуть дані, на деякий час «вимкнуться» і потім продовжать роботу. Прогноз хибний: програма зависла.

Результат `timeout 5 ./deadlock`:

```
Thread 1: locking mutex1
Thread 2: locking mutex2
Thread 1: locking mutex2
Thread 2: locking mutex1
exit code: 124
```

Код 124 означає, що `timeout` зупинив програму, бо вона не завершилась. Після двох останніх рядків «critical section» не з'явився. Стан threads завислої програми: `ls /proc/PID/task | wc -l` дав 3 (main і два worker), і всі три мали стан `S` (sleeping): жоден не виконує роботу, усі чекають.

| Характеристика | Race Condition | Deadlock |
|---|---|---|
| Threads продовжують execution? | так | ні, зупиняються |
| Результат може бути неправильним? | так | результату немає, програма не завершується |
| Програма може повністю перестати прогресувати? | ні | так |
| Пов'язано з timing/order? | так | так |
| Mutex може допомогти? | так | ні, сам mutex може його спричинити |
| Неправильне використання mutex може бути причиною? | так (немає захисту або він недостатній) | так (різний порядок захоплення) |

## 11. Виправлення deadlock

У `deadlock_fixed.c` обидва threads захоплюють mutex в одному порядку: спочатку `mutex1`, потім `mutex2`. Результат:

```
Thread 1: locking mutex1
Thread 2: locking mutex1
Thread 1: locking mutex2
Thread 1: critical section
Thread 2: locking mutex2
Thread 2: critical section
exit code: 0
```

Програма завершилась (код 0). Thread 2 при спробі захопити `mutex1` просто чекає, поки Thread 1 віддасть обидва mutex, і тільки тоді продовжує. Так усунено умову **circular wait**: циклічного очікування більше немає.

## 12. Результат `parallel_sum`

```
Thread 1: 1 ... 250000 = 31250125000
Thread 2: 250001 ... 500000 = 93750125000
Thread 3: 500001 ... 750000 = 156250125000
Thread 4: 750001 ... 1000000 = 218750125000
Parallel result: 500000500000
Expected result: 500000500000
Correct: YES
```

Перевірка за формулою N(N+1)/2 для N = 1 000 000 дає 500000500000.

Додаткове завдання, час:

| N | sequential | 4 threads |
|---|---|---|
| 1 000 000 | 0.004 s | 0.005 s |
| 1 000 000 000 | 2.587 s | 1.509 s |

Для малого N threads не допомогли (навіть трохи повільніше через створення threads). Для великого N 4 threads дали прискорення приблизно в 1,7 раза (ідеал для 2 ядер був би 2). Parallelization має сенс, коли роботи достатньо багато, її можна розділити на незалежні частини, і є кілька ядер.

## 13. Shared vs local data у `parallel_sum`

- **Shared:** масив `Task tasks[]` доступний main і worker threads. Кожен worker читає лише свій елемент (`start`, `end`) і пише лише свій `result`.
- **Thread-local:** змінна `sum` усередині `calculate_sum()` лежить у stack конкретного thread.
- **Mutex у циклі не потрібен**, бо кожен thread змінює лише власний local accumulator, і двох threads, що пишуть в одну змінну одночасно, немає.
- **Main читає результати** лише після `pthread_join()`, коли відповідний thread уже завершився.
- Такий design кращий за один global counter з lock на кожній ітерації, бо майже немає shared mutable state, а отже й synchronization overhead. Дуже часто краще зменшити кількість спільних змінних, ніж додавати більше locks.

## 14. Відповіді на контрольні питання

1. **Thread** — одиниця виконання всередині process зі своїм stack та станом регістрів.
2. Process має власний address space, а threads одного process працюють в одному спільному address space і створюються дешевше.
3. Threads одного process поділяють code, global/static дані, heap і відкриті файли.
4. Кожен thread має власний stack, регістри (зокрема лічильник інструкцій) і власний ідентифікатор.
5. Так.
6. Так, heap спільний (`shared_heap`: worker і main бачили той самий `data`).
7. `pthread_create()` створює новий thread, який починає виконувати вказану функцію.
8. `pthread_join()` чекає завершення thread і дозволяє забрати його результат.
9. Ні. Порядок визначає scheduler (у `multiple_threads` порядок змінювався).
10. **Concurrency**: кілька задач просуваються одночасно в часі (можливо, перемикаючись на одному ядрі). **Parallelism**: задачі реально виконуються одночасно на різних ядрах.
11. **Shared state** — дані, до яких мають доступ кілька threads (наприклад, `counter`).
12. **Race condition** — ситуація, коли результат залежить від порядку та часу виконання threads без належної synchronization.
13. **Lost update** — одне оновлення затирає інше, бо обидва threads прочитали старе значення.
14. Бо `counter++` це три кроки (read, add, write), між якими threads можуть перемкнутись.
15. **Critical section** — ділянка коду, яка працює зі shared state і має виконуватися лише одним thread одночасно.
16. **Mutual exclusion** — гарантія, що в critical section у кожен момент не більше одного thread.
17. **Mutex** — об'єкт, який забезпечує mutual exclusion (захоплюється перед critical section і віддається після).
18. `pthread_mutex_lock()` захоплює mutex або блокує thread, якщо mutex уже захоплений іншим.
19. Thread блокується і чекає, поки власник віддасть mutex.
20. Щоб віддати mutex, інакше інші threads чекатимуть вічно.
21. Бо інші threads довго чекають, і паралельність зникає (як у варіанті з lock навколо всього циклу).
22. **Lock contention** — змагання кількох threads за один mutex, через що вони чекають.
23. Бо ядер обмежена кількість (у мене 2), а threads змагаються за locks і додають overhead створення та перемикання (`mutex_four` не швидший за `mutex_counter`).
24. **Deadlock** — стан, коли threads чекають один одного і жоден не може продовжити.
25. Race condition дає неправильний результат, але програма працює далі, а deadlock повністю зупиняє прогрес.
26. **Circular wait** — замкнене коло очікування: кожен thread чекає ресурс, яким володіє наступний у колі.
27. Якщо всі threads захоплюють locks в одному порядку, цикл очікування виникнути не може.
28. **Starvation** — thread не може отримати потрібний ресурс (наприклад, mutex), бо його постійно займають інші.
29. Local accumulation зменшує synchronization: threads рахують у власних змінних і лише в кінці об'єднують результати, а не блокуються на кожній ітерації.
30. Бо race condition залежить від timing, і успішні запуски лише означають, що поганий порядок не трапився. У `race` два запуски з п'яти дали 2000000, хоча програма некоректна.

## 15. Висновок

У цій лабораторній я створив threads через POSIX Threads і побачив, що вони діляться code, global data та heap, а stack у кожного власний (різні адреси `local`). Експеримент `race.c` показав race condition і lost update: `counter++` складається з трьох instructions, і результат був 1282046, 1702983 та 1940494 замість 2000000. Mutex виправив результат, але зробив програму приблизно в 7–9 разів повільнішою через contention. Різний порядок захоплення двох mutex призвів до deadlock (circular wait), а однаковий порядок його усунув. У `parallel_sum` кожен thread рахує власну суму, тому mutex не потрібен, і для великого N це дало приблизно 1,7-кратне прискорення. Мої прогнози збіглися лише на половину але практичне відтворення прогнозів дали розуміння що не так у хибних прогнозах та реальний доказ у вірних прогнозах.
